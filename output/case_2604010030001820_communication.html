최근 메일에서는 내부 로그에서 timeout 가능성을 뒷받침하는 thread를 찾았고, RowsFetchedPerBlock / SocketTimeout 설정이 관련 있는지 문의하셨습니다.

Cause



What Happens




Client drops the connection



The customer's app or a network device between the client and Storage closes the connection unexpectedly. HTTP.sys responds with a TCP Reset.




Connection goes idle



The connection sits inactive for too long (including during a TLS handshake). HTTP.sys cleans it up with a TCP Reset.

요약하자면 Client가 Idle 이거나 예기치 못한(unexpectedly) 상황에서 TCP RST을 전달합니다.

Cause



What Happens

1. 문제 설명 (Problem Statement)

Databricks Cloud Fetch를 통해 Azure Blob Storage(dbstorage4ub5dfypotv2g)에서 데이터를 병렬 다운로드할 때, 총 동시 연결 수가 128개를 초과하면 서버 측에서 TCP RST 패킷을 전송하여 'Connection reset' 에러가 발생합니다.

이 제한은 단일 빌드뿐 아니라 동일 Storage Account에 대한 모든 동시 빌드의 연결을 합산하여 적용됩니다. 즉, 빌드 A(128 연결) + 빌드 B(128 연결) = 총 256 연결 → Connection Reset 발생.

현재 이 Connection Reset의 원인이 Azure Blob Storage의 자체 제한(throttling) 인지, 또는 네트워크 경로 상의 중간 구성요소(NSG, Azure Firewall, UDR, NIC 등) 에서 발생하는 제한인지가 불명확합니다. TCP allowlisting이 비활성화(DISABLED)된 상태에서는 각 executor가 Storage에 독립적인 TCP 세션을 직접 수립하며, 중간 프록시/게이트웨이 레이어가 제거된 환경입니다. 이 상태에서 128 연결까지는 안정적으로 동작하나 256 연결 이상에서 즉시 실패하는 점은 Storage 레이어 또는 네트워크 레이어 어느 쪽의 제한인지 양쪽 모두 진단이 필요합니다.
