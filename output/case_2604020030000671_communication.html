That timeout is enforced on the Databricks (server) side: the warehouse automatically closes a command when the client sends no requests for results for about 20 minutes. RowsFetchedPerBlock and SocketTimeout are both client-side settings, so they cannot extend or reset that server-side timer. Two extra points worth knowing: the properties page you referenced documents the newer Databricks JDBC driver (version 3 and above), whereas your application is on driver 2.7.3.1010, an older driver where those exact property names do not apply the same way; and RowsFetchedPerBlock only affects "inline" results, which does not cover your case because your large result sets are delivered through Cloud Fetch (files downloaded directly from cloudstorage). In short, the queries themselves are healthy and finish in about 20 minutes; the timeout is triggered specifically when the client goes roughly 20 minutes without requesting more results, at which point the server closes the command. It is the gap in client activity that trips the timer, not the total time the retrieval takes. The very large result sets are the backdrop that makes a long, on-and-off retrieval more likely, but a retrieval that keeps requesting results continuously would not time out.

 

Summary:-

On the Databricks side, the queries complete successfully, and the client begins fetching the results. However, after approximately 20 minutes, there is no further activity from the client side. When the client remains inactive for an extended period, Databricks closes the command due to a timeout and returns a timeout error.

 

Here is what we recommend:

- Make sure the client keeps requesting results continuously throughout the extract, without a pause approaching 20 minutes. If the Foundry extract pauses between fetches, that idle gap is what allows the server to close the command.

 - Upgrade your JDBC driver. Databricks recommends moving from the older 2.x driver you are on (2.7.3.1010) to the latest Databricks JDBC driver, which is documented to provide faster large-result retrieval and more robust handling of large Cloud Fetch downloads. 네트워크 관점

Cloud Fetch 실행 시 클라이언트에서 파일을 fetch 하는 대상이 Databricks 의 managed storage 입니다. Managed storage 가 VM 과 네트워크 구성이 어떻게 되어 있는지에 따라 Traffic 이 점검 포인트가 다를 수 있습니다.
Managed storage 가 public 접근 일때 : public 접근일 때 VM 이 VNet 안에서 동작하고, Firewall 을 사용한다는 가정하에 Traffic 은 “Managed storage --> Firewall --> VNet --> VM“ 로 흐를 것으로 보입니다. 이 때는 Azure 부분을 제외하면 Firewall 의 이슈가 있을 수 있습니다.
Managed storage 가 private (PE 혹은 Service Endpoint 통신일때) : 이때 Traffic 은 “Managed storage --> Azure Backbone --> VNet --> VM” 으로 고객이 따로 검증하는 Traffic 은 없을 것으로 보입니다.
VM 도 SKU 에 따라 네트워크throughput 의 limit 이 있습니다. 이슈가 발생한 시간에 VM 의 네트워크 메트릭을 이용하여 throughput 을 모니터링하여 VM 의 limit 을 모니털이할 수 있고, 필요시 SKU 를 scale up 하여 VM network bandwidth 를 조정해 볼 수 있습니다. (Azure Virtual Machine Network Throughput and Bandwidth | Microsoft Learn [protect2.fireeye.com])  
이외에 중간에 VM 전에 사용되는 기타 게이트웨이 등이 있다면 이 부분도 모니터링대상이 될 수 있습니다.

대용량의 데이터를 처리하는데 이슈가 있다면 이슈 발생 시간의 VM 의 CPU/Memory/Network 등을 모니터링하여 기본적인 VM 이슈를 확인할 수 있습니다. 이를 위해 Azure portal 에서 VM -> Monitor 에서 VM 의 상태를 모니터링할 수 있습니다.
이슈가 되는 VM 에서 Java 어플리케이션을 이용하여 Cloud Fetch 와 비슷한 시나리오를 구성하여 샘플로 테스트 하여 Storage account 와 통신시 잠재적 이슈를 확인해 볼 수 있습니다. 유선상으로 말씀하신 것 처럼 하나의 링크 사이즈 (30GB) 가 12~13개 링크에서 동시에 다운되는 시나리오면, 비슷한 시나리오를 구성하여 VM 에서 테스트 해보고 VM 의 상태를 확인해 보는 것을 추천드립니다.

아래는 Databricks 의 Job 에 대한 분석 원문을 첨부해 드리오니, 참고 부탁드립니다.

**Environment**
- Warehouse: ab1c3bdd8b555ee0 (PRO, DBSQL 2025.40, Current channel)
- Cluster: 0401-000111-2wm7zjj9 (8 workers, healthy, no errors)
- Client: Palantir Foundry via DatabricksJDBCDriver 2.7.3

**Root Cause: CommandInactivityTimeout during CloudFetch result retrieval**

All three queries are identical (same query hash — Palantir Foundry is retrying on each failure) and completed execution successfully on the Databricks side. The platform uploaded ~16,000 Azure Blob Storage result files (totalling ~175 GB compressed, ~394 GB uncompressed, 161 million rows, 268 columns) for each query.

The timeout occurs during the result fetch phase, not during query execution. In CloudFetch mode, Palantir Foundry downloads result files directly from Azure Blob Storage without calling the Databricks Thrift server between each file batch. When the time between consecutive fetch API calls exceeds the warehouse's commandInactivityTimeout threshold, Databricks closes the operation — even though the client is still actively downloading data.

**Evidence:**
- Query 1: 964 fetch API calls made, 274 GB (69%) downloaded before timeout
- Query 2: 164 fetch API calls made, 46 GB (12%) downloaded before timeout
- Query 3: 899 fetch API calls made, 255 GB (65%) downloaded before timeout
- Cluster and warehouse showed no errors — platform-side was healthy

**Recommended Actions**

1. Upgrade the Databricks JDBC Driver in Palantir Foundry
The current version (2.7.3) is significantly outdated. Newer versions include improved CloudFetch batch management which reduces inter-batch gaps. Please coordinate with Palantir to upgrade to the latest available driver version.

2. (Advisory) Review query result volume
161 million rows across 268 columns per query is an exceptionally large result set. We also observed that ~420 out of ~425 result partitions are empty, indicating significant data skew in the upstream tables. Applying tighter filters or pre-aggregating data before extraction would substantially reduce transfer time and eliminate the risk of timeouts entirely.
