주신 추가문의에 대해 답변 드리면,
만약 특정 zone down 이 발생하고, 고객님의 노드풀이 마침 문제의 down 된 zone 으로 노드 생성이 시도된다면(CA 특성상 어느 노드로 zone 배치가 될진 알 수 없기에) 결국 allocation failure 가 발생하게 될 것이고, 이 경우는 할당이 안될 것이기 때문에 그대로 scale up 시도는 멈추게 될 걸로 보입니다.
예로 들어 다시 설명 드리면, zone 1,2,3 중 zone 1 이 down 되어있는 상황이 있다라고 가정할 때, CA 가 마침 zone 1 로 scale up 시도를 하게 되면 할당 실패가 되고 그대로 멈추게 될 가능성이 높습니다. 만약 zone 2 또는 3 으로 scale up 이 시도된다면 문제없이 노드가 생성되겠으나, 33% 의 실패 가능성이 있다면 이 방법은 무리가 있지 않을까 생각 됩니다.


따라서 이와 같은 특정 zone down 장애에 대비해서는, 한 노드풀에서 zone 1,2,3 을 사용하도록 구성할 경우 scale up 이 시도되다가 멈추는 경우가 발생할 수 있으므로, 각 노드풀을 각 zone 에 하나씩 만들어 두고 --balance-similar-node-groups 옵션을 사용하시어 특정 zone down 이 발생하더라도 다른 zone 에 있는 노드풀에 강제로(수동으로) scale up 을 하여 가용량 확보가 될수 있도록 해 주시는 방안이 더 나은 방안이 될 것 같습니다.

- 질문 1 : --min-count와 --max-count가 같은 값으로 고정된 경우 일부 노드가 zone 장애로 NotReady 상태가 되어도 Cluster Autoscaler는 스케일업을 시도하지 않은 것이 맞을까요 ? (VMSS의 target instance count가 이미 max와 같기 때문에) 이 경우 실제로 여유 capacity를 확보하려면 --max-count를 올리는 것 외에 다른 방법이 있을까요 ?

-> 답변 : 말씀 주신 내용은 Cluster Autoscaler 와는 별개로 AKS 자체적으로 remediator 라는 self-healing 을 담당하는 컴포넌트가 존재하기에, 이러한 not ready 된 노드에 대해 스스로 복구를 시도하게 됩니다. 즉, Cluster autoscaler 의 동작과는 별개이며, remediator 는 노드의 상태를 지속적으로 모니터링 하다가 만약 not ready 상태가 된 노드가 감지될 시 노드 reboot -> reimage -> redeploy 순으로 복구절차를 시작합니다. 따라서 고객님께서는 장애로 인한 노드가 not ready 가 되는 상황에 대해서는 우려하지 않으셔도 되며, Cluster autoscaler 는 그와 별개로 니즈에 맞게 설정하여 사용해 주시면 됩니다.

 

- 질문 2 : 단일 node pool이 여러 zone(1,2,3)에 걸쳐 있을 때, Cluster Autoscaler는 zone-aware하지 않아 스케일업 시 어느 zone에 새 노드가 뜰지 제어할 수 없다고 문서에 나와있습니다. zone 장애 상황에서 실제로 zone당 별도 node pool로 나누는 것이 zone-down 복원력 확보에 필수적인 권장사항이 맞을까요 ? 아니면 --balance-similar-node-groups=True 만으로도 충분한 경우가 있을까요 ?

-> 답변 : 말씀 주신대로 단일 nodepool 내의 노드가 zone 1, 2, 3 에 나누어 배치되어 있을 때, 새 노드가 scale out 되면 어느 zone 에 뜰지는 알 수가 없습니다. Zone 에 분산 배치를 하는 이유가 일반적으로 장애를 대비한 고가용성이 목적인데, --balance-similar-node-groups 옵션을 사용하시면 scale out 시 노드 수가 가장 적게 배치되어 있는 zone 에 노드 수를 늘려 이쪽으로 pod 가 배치될 수 있도록 하여 최대한 pod 가 zone 에 고루 분산 배치 될 수 있도록 합니다.

 

--balance-similar-node-groups 옵션이 다소 헷갈릴 수 있는 부분이 있어 다시 설명 드려보자면,

해당 기능은 사전에 nodepool A 를 zone 1 에, nodepool B 를 zone 2 에, 그리고 nodepool C 는 zone 3 과 같이 각 노드풀을 각 zone 에 하나씩 만들어 두신 상태에서 활성화를 해야하며, 이와 같이 구성 후 활성화를 해 주시면 그 후 pending pod 가 있을 때에 아래와 같은 방식으로 동작하여 가급적 각 노드풀에 있는 노드 수를 비슷하게 유지하려 하게 됩니다.

상황



동작




Pending pod 1개 → 노드 1개만 필요



3개의 nodepool 중 현재 노드 수가 가장 적은 풀에 노드 1개 추가




Pending pod 3개 → 노드 3개 필요



Nodepool A 에 노드 1개 추가, nodepool B 에 노드 1개 추가, nodepool C 에 노드 1개 추가 (균등 분배)




Pending pod 5개 → 노드 5개 필요



Nodepool A 에 노드 2개 추가, nodepool B 에 노드 2개 추가, nodepool C 에 노드 1개 추가 (나누어 떨어지지 않으면 일부가 +1 더)

이와 같은 동작은 위에서 말씀 드린대로 pod 를 최대한 각 zone 에 분산 배치 하기 위함입니다.

고객님께서는 특정 zone 이 장애가 발생해 해당 zone 전체가 가용이 어려워졌을 때를 말씀 주신걸로 이해되는데, 이 경우는 사실 nodepool 을 하나로 하여 zone 1,2,3 을 사용하는 노드로 운영을 할 때보다는 --balance-similar-node-groups 옵션을 사용했을 때 노드들이 각 zone 에 더 고루 분포 되어있으니 특정 zone 장애 시 down 되는 노드 수가 더 적어 장애로부터 임팩이 덜 발생하게 되지 않을까 생각 됩니다. 예를 들어 말씀 드려보자면, 한 nodepool 에 zone 1,2,3 을 사용하는 노드가 있을 때에는 각 zone 에 노드가 고르게 분포되어있지 않을 수 있어 zone 1 에는 노드 3대, zone 2에는 노드 2대, zone 3 에는 노드 1대와 같이 존재하게 될 수 있습니다. 이 경우 zone 1 전체에 장애가 발생하면 6대의 노드 중 3대의 노드가 down 되기 때문에 가용이 절반이 되게 됩니다. 하지만 --balance-similar-node-groups 옵션을 사용하여 각 노드풀로 구성을 해두었다면 zone 1 에 노드 2대, zone 2 에 노드 2대, zone 3 에 노드 2대 와 같이 구성이 되어있을테니 zone 1에 있는 노드 2대만 임팩을 받아 조금 더 나은 상황이 될 수 있을 것 같습니다.

 

물론 장애라는 것이 여러 상황이 발생할 수 있어 상황에 따라 임팩의 정도는 달라질 수 있겠으나, 평소에도 고르게 분산 배치를 할 목적으로 --balance-similar-node-groups 옵션을 사용하시는것은 좋은 방법이며 권고되는 방법임을 말씀 드립니다.

- 질문 1 : --min-count와 --max-count가 같은 값으로 고정된 경우 일부 노드가 zone 장애로 NotReady 상태가 되어도 Cluster Autoscaler는 스케일업을 시도하지 않은 것이 맞을까요 ? (VMSS의 target instance count가 이미 max와 같기 때문에) 이 경우 실제로 여유 capacity를 확보하려면 --max-count를 올리는 것 외에 다른 방법이 있을까요 ?

-> 답변 : 말씀 주신 내용은 Cluster Autoscaler 와는 별개로 AKS 자체적으로 remediator 라는 self-healing 을 담당하는 컴포넌트가 존재하기에, 이러한 not ready 된 노드에 대해 스스로 복구를 시도하게 됩니다. 즉, Cluster autoscaler 의 동작과는 별개이며, remediator 는 노드의 상태를 지속적으로 모니터링 하다가 만약 not ready 상태가 된 노드가 감지될 시 노드 reboot -> reimage -> redeploy 순으로 복구절차를 시작합니다. 따라서 고객님께서는 장애로 인한 노드가 not ready 가 되는 상황에 대해서는 우려하지 않으셔도 되며, Cluster autoscaler 는 그와 별개로 니즈에 맞게 설정하여 사용해 주시면 됩니다.

 

- 질문 2 : 단일 node pool이 여러 zone(1,2,3)에 걸쳐 있을 때, Cluster Autoscaler는 zone-aware하지 않아 스케일업 시 어느 zone에 새 노드가 뜰지 제어할 수 없다고 문서에 나와있습니다. zone 장애 상황에서 실제로 zone당 별도 node pool로 나누는 것이 zone-down 복원력 확보에 필수적인 권장사항이 맞을까요 ? 아니면 --balance-similar-node-groups=True 만으로도 충분한 경우가 있을까요 ?

-> 답변 : 말씀 주신대로 단일 nodepool 내의 노드가 zone 1, 2, 3 에 나누어 배치되어 있을 때, 새 노드가 scale out 되면 어느 zone 에 뜰지는 알 수가 없습니다. --balance-similar-node-groups 옵션이 다소 헷갈릴 수 있는 부분이 있어 다시 설명 드려보자면,

해당 기능은 사전에 nodepool A 를 zone 1 에, nodepool B 를 zone 2 에, 그리고 nodepool C 는 zone 3 과 같이 각 노드풀을 각 zone 에 하나씩 만들어 두신 상태에서 활성화를 해야하며, 이와 같이 구성 후 활성화를 해 주시면 그 후 pending pod 가 있을 때에 아래와 같은 방식으로 동작하여 가급적 각 노드풀에 있는 노드 수를 비슷하게 유지하려 하게 됩니다.

상황



동작




Pending pod 1개 → 노드 1개만 필요



3개의 nodepool 중 현재 노드 수가 가장 적은 풀에 노드 1개 추가




Pending pod 3개 → 노드 3개 필요



Nodepool A 에 노드 1개 추가, nodepool B 에 노드 1개 추가, nodepool C 에 노드 1개 추가 (균등 분배)




Pending pod 5개 → 노드 5개 필요



Nodepool A 에 노드 2개 추가, nodepool B 에 노드 2개 추가, nodepool C 에 노드 1개 추가 (나누어 떨어지지 않으면 일부가 +1 더)

이와 같은 동작은 위에서 말씀 드린대로 pod 를 최대한 각 zone 에 분산 배치 하기 위함입니다.

- 질문 1 : --min-count와 --max-count가 같은 값으로 고정된 경우 일부 노드가 zone 장애로 NotReady 상태가 되어도 Cluster Autoscaler는 스케일업을 시도하지 않은 것이 맞을까요 ? (VMSS의 target instance count가 이미 max와 같기 때문에) 이 경우 실제로 여유 capacity를 확보하려면 --max-count를 올리는 것 외에 다른 방법이 있을까요 ?

-> 답변 : 말씀 주신 내용은 Cluster Autoscaler 와는 별개로 AKS 자체적으로 remediator 라는 self-healing 을 담당하는 컴포넌트가 존재하기에, 이러한 not ready 된 노드에 대해 스스로 복구를 시도하게 됩니다. 즉, Cluster autoscaler 의 동작과는 별개이며, remediator 는 노드의 상태를 지속적으로 모니터링 하다가 만약 not ready 상태가 된 노드가 감지될 시 노드 reboot -> reimage -> redeploy 순으로 복구절차를 시작합니다. 따라서 고객님께서는 장애로 인한 노드가 not ready 가 되는 상황에 대해서는 우려하지 않으셔도 되며, Cluster autoscaler 는 그와 별개로 니즈에 맞게 설정하여 사용해 주시면 됩니다.

 

- 질문 2 : 단일 node pool이 여러 zone(1,2,3)에 걸쳐 있을 때, Cluster Autoscaler는 zone-aware하지 않아 스케일업 시 어느 zone에 새 노드가 뜰지 제어할 수 없다고 문서에 나와있습니다. zone 장애 상황에서 실제로 zone당 별도 node pool로 나누는 것이 zone-down 복원력 확보에 필수적인 권장사항이 맞을까요 ? 아니면 --balance-similar-node-groups=True 만으로도 충분한 경우가 있을까요 ?

-> 답변 : 말씀 주신대로 단일 nodepool 내의 노드가 zone 1, 2, 3 에 나누어 배치되어 있을 때, 새 노드가 scale out 되면 어느 zone 에 뜰지는 알 수가 없습니다. Zone 에 분산 배치를 하는 이유가 일반적으로 장애를 대비한 고가용성이 목적인데, --balance-similar-node-groups 옵션을 사용하시면 scale out 시 노드 수가 가장 적게 배치되어 있는 zone 에 노드 수를 늘려 이쪽으로 pod 가 배치될 수 있도록 하여 최대한 pod 가 zone 에 고루 분산 배치 될 수 있도록 합니다.

 

--balance-similar-node-groups 옵션이 다소 헷갈릴 수 있는 부분이 있어 다시 설명 드려보자면,

해당 기능은 사전에 nodepool A 를 zone 1 에, nodepool B 를 zone 2 에, 그리고 nodepool C 는 zone 3 과 같이 각 노드풀을 각 zone 에 하나씩 만들어 두신 상태에서 활성화를 해야하며, 이와 같이 구성 후 활성화를 해 주시면 그 후 pending pod 가 있을 때에 아래와 같은 방식으로 동작하여 가급적 각 노드풀에 있는 노드 수를 비슷하게 유지하려 하게 됩니다.

상황



동작




Pending pod 1개 → 노드 1개만 필요



3개의 nodepool 중 현재 노드 수가 가장 적은 풀에 노드 1개 추가




Pending pod 3개 → 노드 3개 필요



Nodepool A 에 노드 1개 추가, nodepool B 에 노드 1개 추가, nodepool C 에 노드 1개 추가 (균등 분배)




Pending pod 5개 → 노드 5개 필요



Nodepool A 에 노드 2개 추가, nodepool B 에 노드 2개 추가, nodepool C 에 노드 1개 추가 (나누어 떨어지지 않으면 일부가 +1 더)

이와 같은 동작은 위에서 말씀 드린대로 pod 를 최대한 각 zone 에 분산 배치 하기 위함입니다.

고객님께서는 특정 zone 이 장애가 발생해 해당 zone 전체가 가용이 어려워졌을 때를 말씀 주신걸로 이해되는데, 이 경우는 사실 nodepool 을 하나로 하여 zone 1,2,3 을 사용하는 노드로 운영을 할 때보다는 --balance-similar-node-groups 옵션을 사용했을 때 노드들이 각 zone 에 더 고루 분포 되어있으니 특정 zone 장애 시 down 되는 노드 수가 더 적어 장애로부터 임팩이 덜 발생하게 되지 않을까 생각 됩니다. 예를 들어 말씀 드려보자면, 한 nodepool 에 zone 1,2,3 을 사용하는 노드가 있을 때에는 각 zone 에 노드가 고르게 분포되어있지 않을 수 있어 zone 1 에는 노드 3대, zone 2에는 노드 2대, zone 3 에는 노드 1대와 같이 존재하게 될 수 있습니다. 이 경우 zone 1 전체에 장애가 발생하면 6대의 노드 중 3대의 노드가 down 되기 때문에 가용이 절반이 되게 됩니다. 하지만 --balance-similar-node-groups 옵션을 사용하여 각 노드풀로 구성을 해두었다면 zone 1 에 노드 2대, zone 2 에 노드 2대, zone 3 에 노드 2대 와 같이 구성이 되어있을테니 zone 1에 있는 노드 2대만 임팩을 받아 조금 더 나은 상황이 될 수 있을 것 같습니다.

 

물론 장애라는 것이 여러 상황이 발생할 수 있어 상황에 따라 임팩의 정도는 달라질 수 있겠으나, 평소에도 고르게 분산 배치를 할 목적으로 --balance-similar-node-groups 옵션을 사용하시는것은 좋은 방법이며 권고되는 방법임을 말씀 드립니다.

- 질문 1 : --min-count와 --max-count가 같은 값으로 고정된 경우 일부 노드가 zone 장애로 NotReady 상태가 되어도 Cluster Autoscaler는 스케일업을 시도하지 않은 것이 맞을까요 ? (VMSS의 target instance count가 이미 max와 같기 때문에) 이 경우 실제로 여유 capacity를 확보하려면 --max-count를 올리는 것 외에 다른 방법이 있을까요 ?

-> 답변 : 말씀 주신 내용은 Cluster Autoscaler 와는 별개로 AKS 자체적으로 remediator 라는 self-healing 을 담당하는 컴포넌트가 존재하기에, 이러한 not ready 된 노드에 대해 스스로 복구를 시도하게 됩니다. 즉, Cluster autoscaler 의 동작과는 별개이며, remediator 는 노드의 상태를 지속적으로 모니터링 하다가 만약 not ready 상태가 된 노드가 감지될 시 노드 reboot -> reimage -> redeploy 순으로 복구절차를 시작합니다. 따라서 고객님께서는 장애로 인한 노드가 not ready 가 되는 상황에 대해서는 우려하지 않으셔도 되며, Cluster autoscaler 는 그와 별개로 니즈에 맞게 설정하여 사용해 주시면 됩니다.

 

- 질문 2 : 단일 node pool이 여러 zone(1,2,3)에 걸쳐 있을 때, Cluster Autoscaler는 zone-aware하지 않아 스케일업 시 어느 zone에 새 노드가 뜰지 제어할 수 없다고 문서에 나와있습니다. zone 장애 상황에서 실제로 zone당 별도 node pool로 나누는 것이 zone-down 복원력 확보에 필수적인 권장사항이 맞을까요 ? 아니면 --balance-similar-node-groups=True 만으로도 충분한 경우가 있을까요 ?

-> 답변 : 말씀 주신대로 단일 nodepool 내의 노드가 zone 1, 2, 3 에 나누어 배치되어 있을 때, 새 노드가 scale out 되면 어느 zone 에 뜰지는 알 수가 없습니다. --balance-similar-node-groups 옵션이 다소 헷갈릴 수 있는 부분이 있어 다시 설명 드려보자면,

해당 기능은 사전에 nodepool A 를 zone 1 에, nodepool B 를 zone 2 에, 그리고 nodepool C 는 zone 3 과 같이 각 노드풀을 각 zone 에 하나씩 만들어 두신 상태에서 활성화를 해야하며, 이와 같이 구성 후 활성화를 해 주시면 그 후 pending pod 가 있을 때에 아래와 같은 방식으로 동작하여 가급적 각 노드풀에 있는 노드 수를 비슷하게 유지하려 하게 됩니다.

상황



동작




Pending pod 1개 → 노드 1개만 필요



3개의 nodepool 중 현재 노드 수가 가장 적은 풀에 노드 1개 추가




Pending pod 3개 → 노드 3개 필요



Nodepool A 에 노드 1개 추가, nodepool B 에 노드 1개 추가, nodepool C 에 노드 1개 추가 (균등 분배)




Pending pod 5개 → 노드 5개 필요



Nodepool A 에 노드 2개 추가, nodepool B 에 노드 2개 추가, nodepool C 에 노드 1개 추가 (나누어 떨어지지 않으면 일부가 +1 더)

이와 같은 동작은 위에서 말씀 드린대로 pod 를 최대한 각 zone 에 분산 배치 하기 위함입니다.

고객님께서는 특정 zone 이 장애가 발생해 해당 zone 전체가 가용이 어려워졌을 때를 말씀 주신걸로 이해되는데, 이 경우는 사실 nodepool 을 하나로 하여 zone 1,2,3 을 사용하는 노드로 운영을 할 때보다는 --balance-similar-node-groups 옵션을 사용했을 때 노드들이 각 zone 에 더 고루 분포 되어있으니 특정 zone 장애 시 down 되는 노드 수가 더 적어 장애로부터 임팩이 덜 발생하게 되지 않을까 생각 됩니다. 예를 들어 말씀 드려보자면, 한 nodepool 에 zone 1,2,3 을 사용하는 노드가 있을 때에는 각 zone 에 노드가 고르게 분포되어있지 않을 수 있어 zone 1 에는 노드 3대, zone 2에는 노드 2대, zone 3 에는 노드 1대와 같이 존재하게 될 수 있습니다. 이 경우 zone 1 전체에 장애가 발생하면 6대의 노드 중 3대의 노드가 down 되기 때문에 가용이 절반이 되게 됩니다. 하지만 --balance-similar-node-groups 옵션을 사용하여 각 노드풀로 구성을 해두었다면 zone 1 에 노드 2대, zone 2 에 노드 2대, zone 3 에 노드 2대 와 같이 구성이 되어있을테니 zone 1에 있는 노드 2대만 임팩을 받아 조금 더 나은 상황이 될 수 있을 것 같습니다.

 

물론 장애라는 것이 여러 상황이 발생할 수 있어 상황에 따라 임팩의 정도는 달라질 수 있겠으나, 평소에도 고르게 분산 배치를 할 목적으로 --balance-similar-node-groups 옵션을 사용하시는것은 좋은 방법이며 권고되는 방법임을 말씀 드립니다.

- 질문 1 : --min-count와 --max-count가 같은 값으로 고정된 경우 일부 노드가 zone 장애로 NotReady 상태가 되어도 Cluster Autoscaler는 스케일업을 시도하지 않은 것이 맞을까요 ? (VMSS의 target instance count가 이미 max와 같기 때문에) 이 경우 실제로 여유 capacity를 확보하려면 --max-count를 올리는 것 외에 다른 방법이 있을까요 ?

-> 답변 : 말씀 주신 내용은 Cluster Autoscaler 와는 별개로 AKS 자체적으로 remediator 라는 self-healing 을 담당하는 컴포넌트가 존재하기에, 이러한 not ready 된 노드에 대해 스스로 복구를 시도하게 됩니다. 즉, Cluster autoscaler 의 동작과는 별개이며, remediator 는 노드의 상태를 지속적으로 모니터링 하다가 만약 not ready 상태가 된 노드가 감지될 시 노드 reboot -> reimage -> redeploy 순으로 복구절차를 시작합니다. 따라서 고객님께서는 장애로 인한 노드가 not ready 가 되는 상황에 대해서는 우려하지 않으셔도 되며, Cluster autoscaler 는 그와 별개로 니즈에 맞게 설정하여 사용해 주시면 됩니다.

 

- 질문 2 : 단일 node pool이 여러 zone(1,2,3)에 걸쳐 있을 때, Cluster Autoscaler는 zone-aware하지 않아 스케일업 시 어느 zone에 새 노드가 뜰지 제어할 수 없다고 문서에 나와있습니다. zone 장애 상황에서 실제로 zone당 별도 node pool로 나누는 것이 zone-down 복원력 확보에 필수적인 권장사항이 맞을까요 ? 아니면 --balance-similar-node-groups=True 만으로도 충분한 경우가 있을까요 ?

-> 답변 : 말씀 주신대로 단일 nodepool 내의 노드가 zone 1, 2, 3 에 나누어 배치되어 있을 때, 새 노드가 scale out 되면 어느 zone 에 뜰지는 알 수가 없습니다. Zone 에 분산 배치를 하는 이유가 일반적으로 장애를 대비한 고가용성이 목적인데, --balance-similar-node-groups 옵션을 사용하시면 scale out 시 노드 수가 가장 적게 배치되어 있는 zone 에 노드 수를 늘려 이쪽으로 pod 가 배치될 수 있도록 하여 최대한 pod 가 zone 에 고루 분산 배치 될 수 있도록 합니다.

 

--balance-similar-node-groups 옵션이 다소 헷갈릴 수 있는 부분이 있어 다시 설명 드려보자면,

해당 기능은 사전에 nodepool A 를 zone 1 에, nodepool B 를 zone 2 에, 그리고 nodepool C 는 zone 3 과 같이 각 노드풀을 각 zone 에 하나씩 만들어 두신 상태에서 활성화를 해야하며, 이와 같이 구성 후 활성화를 해 주시면 그 후 pending pod 가 있을 때에 아래와 같은 방식으로 동작하여 가급적 각 노드풀에 있는 노드 수를 비슷하게 유지하려 하게 됩니다.

상황



동작




Pending pod 1개 → 노드 1개만 필요



3개의 nodepool 중 현재 노드 수가 가장 적은 풀에 노드 1개 추가




Pending pod 3개 → 노드 3개 필요



Nodepool A 에 노드 1개 추가, nodepool B 에 노드 1개 추가, nodepool C 에 노드 1개 추가 (균등 분배)




Pending pod 5개 → 노드 5개 필요



Nodepool A 에 노드 2개 추가, nodepool B 에 노드 2개 추가, nodepool C 에 노드 1개 추가 (나누어 떨어지지 않으면 일부가 +1 더)

이와 같은 동작은 위에서 말씀 드린대로 pod 를 최대한 각 zone 에 분산 배치 하기 위함입니다.

고객님께서는 특정 zone 이 장애가 발생해 해당 zone 전체가 가용이 어려워졌을 때를 말씀 주신걸로 이해되는데, 이 경우는 사실 nodepool 을 하나로 하여 zone 1,2,3 을 사용하는 노드로 운영을 할 때보다는 --balance-similar-node-groups 옵션을 사용했을 때 노드들이 각 zone 에 더 고루 분포 되어있으니 특정 zone 장애 시 down 되는 노드 수가 더 적어 장애로부터 임팩이 덜 발생하게 되지 않을까 생각 됩니다. 예를 들어 말씀 드려보자면, 한 nodepool 에 zone 1,2,3 을 사용하는 노드가 있을 때에는 각 zone 에 노드가 고르게 분포되어있지 않을 수 있어 zone 1 에는 노드 3대, zone 2에는 노드 2대, zone 3 에는 노드 1대와 같이 존재하게 될 수 있습니다. 이 경우 zone 1 전체에 장애가 발생하면 6대의 노드 중 3대의 노드가 down 되기 때문에 가용이 절반이 되게 됩니다. 하지만 --balance-similar-node-groups 옵션을 사용하여 각 노드풀로 구성을 해두었다면 zone 1 에 노드 2대, zone 2 에 노드 2대, zone 3 에 노드 2대 와 같이 구성이 되어있을테니 zone 1에 있는 노드 2대만 임팩을 받아 조금 더 나은 상황이 될 수 있을 것 같습니다.

 

물론 장애라는 것이 여러 상황이 발생할 수 있어 상황에 따라 임팩의 정도는 달라질 수 있겠으나, 평소에도 고르게 분산 배치를 할 목적으로 --balance-similar-node-groups 옵션을 사용하시는것은 좋은 방법이며 권고되는 방법임을 말씀 드립니다.

- 질문 1 : --min-count와 --max-count가 같은 값으로 고정된 경우 일부 노드가 zone 장애로 NotReady 상태가 되어도 Cluster Autoscaler는 스케일업을 시도하지 않은 것이 맞을까요 ? (VMSS의 target instance count가 이미 max와 같기 때문에) 이 경우 실제로 여유 capacity를 확보하려면 --max-count를 올리는 것 외에 다른 방법이 있을까요 ?

-> 답변 : 말씀 주신 내용은 Cluster Autoscaler 와는 별개로 AKS 자체적으로 remediator 라는 self-healing 을 담당하는 컴포넌트가 존재하기에, 이러한 not ready 된 노드에 대해 스스로 복구를 시도하게 됩니다. 즉, Cluster autoscaler 의 동작과는 별개이며, remediator 는 노드의 상태를 지속적으로 모니터링 하다가 만약 not ready 상태가 된 노드가 감지될 시 노드 reboot -> reimage -> redeploy 순으로 복구절차를 시작합니다. 따라서 고객님께서는 장애로 인한 노드가 not ready 가 되는 상황에 대해서는 우려하지 않으셔도 되며, Cluster autoscaler 는 그와 별개로 니즈에 맞게 설정하여 사용해 주시면 됩니다.

 

- 질문 2 : 단일 node pool이 여러 zone(1,2,3)에 걸쳐 있을 때, Cluster Autoscaler는 zone-aware하지 않아 스케일업 시 어느 zone에 새 노드가 뜰지 제어할 수 없다고 문서에 나와있습니다. zone 장애 상황에서 실제로 zone당 별도 node pool로 나누는 것이 zone-down 복원력 확보에 필수적인 권장사항이 맞을까요 ? 아니면 --balance-similar-node-groups=True 만으로도 충분한 경우가 있을까요 ?

-> 답변 : 말씀 주신대로 단일 nodepool 내의 노드가 zone 1, 2, 3 에 나누어 배치되어 있을 때, 새 노드가 scale out 되면 어느 zone 에 뜰지는 알 수가 없습니다. Zone 에 분산 배치를 하는 이유가 일반적으로 장애를 대비한 고가용성이 목적인데, --balance-similar-node-groups 옵션을 사용하시면 scale out 시 노드 수가 가장 적게 배치되어 있는 zone 에 노드 수를 늘려 이쪽으로 pod 가 배치될 수 있도록 하여 최대한 pod 가 zone 에 고루 분산 배치 될 수 있도록 합니다.

 

--balance-similar-node-groups 옵션이 다소 헷갈릴 수 있는 부분이 있어 다시 설명 드려보자면,

해당 기능은 사전에 nodepool A 를 zone 1 에, nodepool B 를 zone 2 에, 그리고 nodepool C 는 zone 3 과 같이 각 노드풀을 각 zone 에 하나씩 만들어 두신 상태에서 활성화를 해야하며, 이와 같이 구성 후 활성화를 해 주시면 그 후 pending pod 가 있을 때에 아래와 같은 방식으로 동작하여 가급적 각 노드풀에 있는 노드 수를 비슷하게 유지하려 하게 됩니다.

상황



동작




Pending pod 1개 → 노드 1개만 필요



3개의 nodepool 중 현재 노드 수가 가장 적은 풀에 노드 1개 추가




Pending pod 3개 → 노드 3개 필요



Nodepool A 에 노드 1개 추가, nodepool B 에 노드 1개 추가, nodepool C 에 노드 1개 추가 (균등 분배)




Pending pod 5개 → 노드 5개 필요



Nodepool A 에 노드 2개 추가, nodepool B 에 노드 2개 추가, nodepool C 에 노드 1개 추가 (나누어 떨어지지 않으면 일부가 +1 더)

이와 같은 동작은 위에서 말씀 드린대로 pod 를 최대한 각 zone 에 분산 배치 하기 위함입니다.

고객님께서는 특정 zone 이 장애가 발생해 해당 zone 전체가 가용이 어려워졌을 때를 말씀 주신걸로 이해되는데, 이 경우는 사실 nodepool 을 하나로 하여 zone 1,2,3 을 사용하는 노드로 운영을 할 때보다는 --balance-similar-node-groups 옵션을 사용했을 때 노드들이 각 zone 에 더 고루 분포 되어있으니 특정 zone 장애 시 down 되는 노드 수가 더 적어 장애로부터 임팩이 덜 발생하게 되지 않을까 생각 됩니다. 예를 들어 말씀 드려보자면, 한 nodepool 에 zone 1,2,3 을 사용하는 노드가 있을 때에는 각 zone 에 노드가 고르게 분포되어있지 않을 수 있어 zone 1 에는 노드 3대, zone 2에는 노드 2대, zone 3 에는 노드 1대와 같이 존재하게 될 수 있습니다. 이 경우 zone 1 전체에 장애가 발생하면 6대의 노드 중 3대의 노드가 down 되기 때문에 가용이 절반이 되게 됩니다. 하지만 --balance-similar-node-groups 옵션을 사용하여 각 노드풀로 구성을 해두었다면 zone 1 에 노드 2대, zone 2 에 노드 2대, zone 3 에 노드 2대 와 같이 구성이 되어있을테니 zone 1에 있는 노드 2대만 임팩을 받아 조금 더 나은 상황이 될 수 있을 것 같습니다.

 

물론 장애라는 것이 여러 상황이 발생할 수 있어 상황에 따라 임팩의 정도는 달라질 수 있겠으나, 평소에도 고르게 분산 배치를 할 목적으로 --balance-similar-node-groups 옵션을 사용하시는것은 좋은 방법이며 권고되는 방법임을 말씀 드립니다.

-> 답변 : 말씀 주신대로 단일 nodepool 내의 노드가 zone 1, 2, 3 에 나누어 배치되어 있을 때, 새 노드가 scale out 되면 어느 zone 에 뜰지는 알 수가 없습니다. 해당 기능은 사전에 nodepool A 를 zone 1 에, nodepool B 를 zone 2 에, 그리고 nodepool C 는 zone 3 과 같이 각 노드풀을 각 zone 에 하나씩 만들어 두신 상태에서 활성화를 해야하며, 이와 같이 구성 후 활성화를 해 주시면 그 후 pending pod 가 있을 때에 아래와 같은 방식으로 동작하여 가급적 각 노드풀에 있는 노드 수를 비슷하게 유지하려 하게 됩니다.

이와 같은 동작은 위에서 말씀 드린대로 pod 를 최대한 각 zone 에 분산 배치 하기 위함입니다.

고객님께서는 특정 zone 이 장애가 발생해 해당 zone 전체가 가용이 어려워졌을 때를 말씀 주신걸로 이해되는데, 이 경우는 사실 nodepool 을 하나로 하여 zone 1,2,3 을 사용하는 노드로 운영을 할 때보다는 --balance-similar-node-groups 옵션을 사용했을 때 노드들이 각 zone 에 더 고루 분포 되어있으니 특정 zone 장애 시 down 되는 노드 수가 더 적어 장애로부터 임팩이 덜 발생하게 되지 않을까 생각 됩니다. 예를 들어 말씀 드려보자면, 한 nodepool 에 zone 1,2,3 을 사용하는 노드가 있을 때에는 각 zone 에 노드가 고르게 분포되어있지 않을 수 있어 zone 1 에는 노드 3대, zone 2에는 노드 2대, zone 3 에는 노드 1대와 같이 존재하게 될 수 있습니다. 이 경우 zone 1 전체에 장애가 발생하면 6대의 노드 중 3대의 노드가 down 되기 때문에 가용이 절반이 되게 됩니다. 하지만 --balance-similar-node-groups 옵션을 사용하여 각 노드풀로 구성을 해두었다면 zone 1 에 노드 2대, zone 2 에 노드 2대, zone 3 에 노드 2대 와 같이 구성이 되어있을테니 zone 1에 있는 노드 2대만 임팩을 받아 조금 더 나은 상황이 될 수 있을 것 같습니다.

 

물론 장애라는 것이 여러 상황이 발생할 수 있어 상황에 따라 임팩의 정도는 달라질 수 있겠으나, 평소에도 고르게 분산 배치를 할 목적으로 --balance-similar-node-groups 옵션을 사용하시는것은 좋은 방법이며 권고되는 방법임을 말씀 드립니다.

이와 같은 동작은 위에서 말씀 드린대로 pod 를 최대한 각 zone 에 분산 배치 하기 위함입니다.

고객님께서는 특정 zone 이 장애가 발생해 해당 zone 전체가 가용이 어려워졌을 때를 말씀 주신걸로 이해되는데, 이 경우는 사실 nodepool 을 하나로 하여 zone 1,2,3 을 사용하는 노드로 운영을 할 때보다는 --balance-similar-node-groups 옵션을 사용했을 때 노드들이 각 zone 에 더 고루 분포 되어있으니 특정 zone 장애 시 down 되는 노드 수가 더 적어 장애로부터 임팩이 덜 발생하게 되지 않을까 생각 됩니다. 예를 들어 말씀 드려보자면, 한 nodepool 에 zone 1,2,3 을 사용하는 노드가 있을 때에는 각 zone 에 노드가 고르게 분포되어있지 않을 수 있어 zone 1 에는 노드 3대, zone 2에는 노드 2대, zone 3 에는 노드 1대와 같이 존재하게 될 수 있습니다. 이 경우 zone 1 전체에 장애가 발생하면 6대의 노드 중 3대의 노드가 down 되기 때문에 가용이 절반이 되게 됩니다. 하지만 --balance-similar-node-groups 옵션을 사용하여 각 노드풀로 구성을 해두었다면 zone 1 에 노드 2대, zone 2 에 노드 2대, zone 3 에 노드 2대 와 같이 구성이 되어있을테니 zone 1에 있는 노드 2대만 임팩을 받아 조금 더 나은 상황이 될 수 있을 것 같습니다.

 

물론 장애라는 것이 여러 상황이 발생할 수 있어 상황에 따라 임팩의 정도는 달라질 수 있겠으나, 평소에도 고르게 분산 배치를 할 목적으로 --balance-similar-node-groups 옵션을 사용하시는것은 좋은 방법이며 권고되는 방법임을 말씀 드립니다.
