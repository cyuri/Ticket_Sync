문의 사항: 



Redis Client가 AKS 노드(리눅스)에서 구동중이며, Redis 문서에 명시된 net.ipv4.tcp_retries2 파라미터를 적용하고자 합니다,
https://learn.microsoft.com/en-us/azure/azure-cache-for-redis/cache-best-practices-connection#tcp-settings-for-linux-hosted-client-applications
 
AKS 환경에 Redis Client가 구동중일 경우 해당 설정을 어떻게 적용해야 하는지 가이드 받을 수 있을까요?
 
지난번 2605260030000494 AKS SR 케이스에서 확인한 내용은
unsafe sysctl 허용 목록을 추가한 kubelet config을 가지고 신규 노드풀을 생성한 뒤에
 redis client pod의 securitycontext를 통해 net.ipv4.tcp_retries2 파라미터를 세팅하는 것으로 이해하였습니다.
혹시 해당 방식이 맞을지도 확인 부탁드립니다.
 

 

결과 요약: 

문의주신 내용과 관련하여, 저희 Azure Cache for Redis에서 권장하는 Linux TCP 설정인 net.ipv4.tcp_retries2 적용 방법 및 동작 방식에 대해 다음과 같이 안내드렸습니다.
먼저 Redis Client가 AKS 환경에서 구동되는 경우에는 Kubernetes에서 net.ipv4.tcp_retries2가 unsafe sysctl로 분류되므로, 해당 값을 적용하기 위해서는 allowedUnsafeSysctls가 포함된 kubelet 설정으로 신규 Node Pool을 생성한 후, Redis Client Pod의 securityContext.sysctls를 통해 값을 설정하는 방식이 맞는 것으로 안내드렸습니다.
또한 net.ipv4.tcp_retries2=5는 시간을 의미하는 값이 아니라 Linux 운영체제의 TCP 재전송 동작을 제어하는 커널 파라미터이며, 기본값보다 응답이 없는 TCP 연결을 보다 빠르게 실패로 판단하여 Redis Client가 재연결을 시작할 수 있도록 도와주는 설정임을 설명드렸습니다.
아울러 해당 설정 자체가 Redis 리소스에 직접적인 부하를 발생시키는 것은 아니며, 장애 또는 Failover 발생 시 다수의 Client가 동시에 재연결을 수행하는 경우 일시적인 연결 부하가 발생할 수 있으므로, Exponential Backoff, Jitter, ConnectionMultiplexer 재사용 등의 Client 측 연결 복원 방식을 함께 적용하는 것을 권장드렸습니다.
추가적으로 net.ipv4.tcp_retries2와 StackExchange.Redis의 ForceReconnect Pattern은 서로 다른 계층에서 동작하는 보완적인 기능이며, 일반적인 환경에서는 StackExchange.Redis의 기본 자동 재연결 기능으로 충분한 경우가 많고, ForceReconnect Pattern은 장시간 연결이 복구되지 않는 예외적인 상황에서 고려할 수 있는 복구 방법임을 안내드렸습니다.
마지막으로 해당 net.ipv4.tcp_retries2 설정은 Redis 서비스의 설정이 아닌 Linux Client 운영체제의 TCP 설정이므로, Azure Cache for Redis뿐만 아니라 Azure Managed Redis 환경에서도 동일한 원리로 적용 가능한 설정임을 안내드렸습니다.

추가로 문의해 주신 내용에 대해 확인해보았으며, 아래와 같이 안내드립니다.


먼저 net.ipv4.tcp_retries2 값과 Redis 부하에 대한 부분을 확인해보았을 때, 고객님께서 이해하신 방향은 전반적으로 맞는 것으로 보여집니다.


다만 한 가지 말씀드리고 싶은 부분은 net.ipv4.tcp_retries2=5는 "5분"을 의미하는 값이 아니라, Linux TCP Stack에서 이미 연결된 TCP 세션에 대해 응답이 없는 경우 몇 번의 재전송을 수행한 후 연결 실패로 판단할지를 결정하는 커널 파라미터입니다.
따라서 실제 연결 실패를 감지하는 시간은 네트워크 상태 및 TCP 재전송 타이머에 따라 달라질 수 있습니다.


기본값인 15를 사용할 경우에는 Linux에서 응답이 없는 TCP 연결을 상당 시간 동안 유지하려고 하기 때문에, Redis Client가 이미 끊어진 연결을 인지하기까지 오랜 시간이 소요될 수 있습니다.
반면 5로 설정하면 운영체제가 연결 실패를 보다 빠르게 감지하게 되어 Redis Client도 보다 빠르게 재연결을 시작할 수 있습니다.


다만 해당 설정 자체가 Redis에 지속적으로 새로운 연결을 생성하거나 부하를 발생시키는 것은 아닌 것으로 보여집니다.
Redis 리소스에 대한 부하는 주로 장애나 Failover 이후 다수의 Client가 동시에 재연결을 시도하는 경우 발생할 수 있습니다.


특히 여러 AKS Pod가 동일한 시점에 즉시 재시도를 수행하거나, Exponential Backoff 또는 Jitter 없이 동일한 간격으로 반복적으로 재시도하는 경우에는 일시적으로 Redis 연결 요청이 집중될 수 있습니다.


이에 따라 net.ipv4.tcp_retries2=5 설정과 함께 Client 측에서는 Exponential Backoff 및 Jitter를 적용하여 재연결 시점을 분산시키고, ConnectionMultiplexer를 장기간 재사용하도록 구성하는 것을 권장드립니다.
이러한 구성을 통해 장애 복구 시 Redis 및 Client 측의 일시적인 부하를 효과적으로 줄일 수 있을 것으로 보여집니다.


다음으로 문의주신 ForceReconnect Pattern과의 차이에 대해 안내드립니다.
net.ipv4.tcp_retries2는 Linux 운영체제(TCP Layer)에서 동작하는 설정으로, 응답이 없는 TCP 연결을 운영체제가 얼마나 빠르게 실패로 판단할지를 결정합니다.


반면 ForceReconnect Pattern은 StackExchange.Redis 애플리케이션 계층에서 동작하는 복구 패턴으로, ConnectionMultiplexer가 장시간 정상적으로 복구되지 않는 경우 기존 객체를 새로 생성하여 연결을 복구하는 방식입니다.


즉, 두 기능은 서로 대체하는 관계가 아니라 서로 다른 계층에서 동작하는 보완적인 기능으로 이해해주시면 감사하겠습니다.
또한 net.ipv4.tcp_retries2 값을 조정하지 않은 경우에는 Linux 운영체제가 오랜 시간 동안 TCP 재전송을 계속 수행하게 되어, 애플리케이션에서는 연결 오류 대신 Timeout이 지속적으로 발생할 수 있습니다.


반대로 net.ipv4.tcp_retries2 값을 낮추면 운영체제가 연결 실패를 보다 빠르게 애플리케이션에 전달할 수 있으므로 Redis Client도 보다 빠르게 복구 절차를 시작할 수 있습니다.
일반적인 환경에서는 StackExchange.Redis의 기본 자동 재연결 기능만으로도 충분한 경우가 많으며, ForceReconnect Pattern은 ConnectionMultiplexer가 장시간 정상적으로 복구되지 않는 예외적인 상황에서 추가적으로 고려할 수 있는 복구 방법으로 이해해주시면 감사하겠습니다.


마지막으로 Azure Managed Redis에서도 동일한 내용이 적용되는지에 대해서도 확인해보았습니다.
해당 net.ipv4.tcp_retries2 설정은 Azure Cache for Redis 또는 Azure Managed Redis 서버의 설정이 아니라, Redis Client가 실행되는 Linux 운영체제의 TCP 동작을 제어하는 Client 측 설정입니다.


따라서 Redis Client가 Linux 기반 AKS 환경에서 Azure Managed Redis에 연결하는 경우에도 동일한 원리로 적용되며, Azure Managed Redis 환경에서도 의미 있는 설정으로 보시면 될 것으로 보여집니다.


추가로 궁금하신 Redis 관련 사항이나 확인이 필요하신 부분이 있으시면 언제든지 편하게 회신 부탁드립니다.

https://learn.microsoft.com/en-us/azure/azure-cache-for-redis/cache-best-practices-connection#tcp-settings-for-linux-hosted-client-applications
 
AKS 환경에 Redis Client가 구동중일 경우 해당 설정을 어떻게 적용해야 하는지 가이드 받을 수 있을까요?
 
지난번 2605260030000494 AKS SR 케이스에서 확인한 내용은
unsafe sysctl 허용 목록을 추가한 kubelet config을 가지고 신규 노드풀을 생성한 뒤에
 redis client pod의 securitycontext를 통해 net.ipv4.tcp_retries2 파라미터를 세팅하는 것으로 이해하였습니다.
혹시 해당 방식이 맞을지도 확인 부탁드립니다.

진행 사항: 

문의주신 내용을 확인해보았을때, 고객님께서 이해하고 계신 내용이 맞는 것으로 보여집니다.
Redis Client가 AKS Linux 노드에서 구동되는 환경에서 net.ipv4.tcp_retries2 값을 적용하기 위해서는, 이전 AKS SR에서 안내받으신 것과 같이 unsafe sysctl을 허용하도록 kubelet configuration이 적용된 신규 Node Pool을 생성한 후, Redis Client Pod의 securityContext.sysctls를 통해 net.ipv4.tcp_retries2 값을 설정하는 방식으로 구성하시는 것이 맞습니다.
해당 설정이 필요한 이유는 net.ipv4.tcp_retries2가 Kubernetes에서 unsafe sysctl로 분류되어 기본적으로는 Pod에서 설정이 허용되지 않기 때문입니다.
따라서 먼저 Node Pool의 kubelet에서 해당 sysctl을 허용해야 하며, 이후 각 Redis Client Pod에서 securityContext.sysctls를 통해 값을 적용하는 구조로 동작하게 됩니다.
저희 Azure Redis 관점에서는 Linux 기본값인 net.ipv4.tcp_retries2=15를 사용할 경우, 예기치 않은 Failover 또는 네트워크 장애 발생 시 이미 끊어진 TCP 연결을 Client가 감지하기까지 상당한 시간이 소요될 수 있습니다.
이러한 이유로 저희 Azure Cache for Redis 공식 문서에서는 net.ipv4.tcp_retries2=5 설정을 권장드리고 있습니다.
다만, 문의주신 AKS Node Pool 생성 방법, kubelet의 allowedUnsafeSysctls 설정, Pod securityContext 구성 등 AKS 플랫폼 구성 방법에 대한 부분은 AKS 제품 지원 범위에 해당합니다.
현재 저희 Redis 관점에서는 고객님께서 이해하고 계신 구성 방향이 맞는 것으로 확인되며, 실제 AKS 환경에서의 구현 방법이나 세부 구성에 대해서는 AKS 제품팀에서 가장 정확한 가이드를 제공드릴 수 있을 것으로 판단됩니다.
혹시 해당 부분에 대해 보다 상세한 AKS 구성 가이드가 필요하시다면 AKS 지원팀으로 새로운 지원 케이스를 생성하여 문의해 주시는 것을 권장드립니다.
저희 Azure Redis 관점에서 궁금하신 사항이나 추가로 확인이 필요한 부분이 있으시면 언제든지 편하게 회신 부탁드리겠습니다.
