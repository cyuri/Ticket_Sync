아래 Kernel 로그를 통해 이번 현상의 정확한 원인을 확인할 수 있었습니다.
Out of memory: Killed process 17431 (blobfuse2)

해당 로그는 Linux Kernel의 OOM(Out Of Memory) Killer가 시스템 메모리 부족을 감지하여 BlobFuse2 Process를 강제로 종료하였음을 의미합니다.

BlobFuse2는 Linux FUSE(User-space Filesystem) 기반으로 동작하기 때문에, BlobFuse2 Process가 종료되면 Kernel에는 Mount 정보만 남게 되고 사용자 공간에서 요청을 처리할 Process가 존재하지 않게 됩니다.
따라서 이후에는 Linux에서 "Transport endpoint is not connected" 오류를 반환하게 되며, 이번에도 재마운트 이후 정상적으로 복구된 이유가 이와 동일한 동작 방식 때문으로 확인되었습니다.
즉, 이번 현상의 원인은 저희 Azure Storage 서비스 장애가 아닌 VM 내부 메모리 부족으로 인해 BlobFuse2 Process가 OOM Killer에 의해 종료된 것으로 확인되었습니다.
OOM이 재발하지 않도록 하기 위해서는 아래 사항들을 권장드립니다.
VM 메모리 사용량 모니터링 및 메모리 여유 확보 
먼저 BlobFuse2가 동작하는 VM의 메모리 사용량을 확인 부탁드립니다.
따라서 아래 항목들을 지속적으로 모니터링하시는 것을 권장드립니다.
Available Memory
Free Memory
Swap 사용량
BlobFuse2 Process Memory(RSS)
Application Memory 사용량
Troubleshoot issues in BlobFuse - Azure Storage | Microsoft Learn
이번에 확인된 OOM은 Linux Kernel에서 발생한 메모리 부족으로 인해 BlobFuse2 Process가 종료된 것으로, 저희 Azure Storage 서비스에서 발생한 문제가 아닌 VM 운영체제의 메모리 관리 영역에 해당합니다.
따라서 OOM의 근본 원인(메모리 부족 원인 분석, VM Size 적정성 검토, Linux Memory Tuning 등)에 대해서는 Azure VM(Compute) 팀 또는 Linux 운영체제 담당 부서를 통해 추가적인 검토를 받아보시는 것을 권장드립니다.

진행 사항: 

먼저 저희 내부적으로 Azure Storage Backend 로그 및 서비스 상태를 종합적으로 확인해 보았습니다.

확인 결과, 해당 시간 동안 Storage Account staz01devmagmaload01은 정상적으로 동작하고 있었으며, Service Availability 또한 정상으로 확인되었습니다.

고객님 VM(10.243.194.118)에서 Storage Account로 전달된 요청들도 모두 HTTP 200(Success)으로 정상 처리되었으며, Storage 서비스 측에서는 HTTP 5xx 오류나 Throttling(503)과 같은 서버 측 오류는 확인되지 않았습니다.

따라서 Azure Storage 서비스 자체의 장애나 성능 저하로 인해 발생한 현상은 아닌 것으로 확인되었습니다.

고객님께서 전달해주신 로그를 함께 확인해 보았을 때에는 아래와 같은 점들이 확인되었습니다.

ps -ef | grep blobfuse | grep tbloder2magma 결과에서 해당 Mount를 담당하는 BlobFuse2 Process가 존재하지 않았습니다.
ls 수행 시 d????????? 형태로 표시되었으며, Transport endpoint is not connected 오류가 발생하였습니다.
fuser -vm 결과에서도 Kernel Mount만 존재하고 BlobFuse2 Process는 확인되지 않았습니다.
이후 동일 경로를 재마운트한 이후에는 정상적으로 접근이 가능하였습니다.

위 내용들을 종합해 보았을 때, 이번 현상은 BlobFuse2 Process가 종료된 상태에서 Linux Kernel의 FUSE Mount 정보만 남아있는 Orphaned FUSE Mount 상태가 발생한 것으로 보여집니다.

BlobFuse2는 Linux FUSE(User-space Filesystem)를 사용하여 동작합니다. 일반적으로 BlobFuse2 Process가 어떠한 사유로 종료되었지만 Kernel에는 Mount 정보가 그대로 남아있는 경우에는 Kernel이 더 이상 사용자 공간의 BlobFuse2 Process와 통신하지 못하게 되며, 이 경우 Linux에서는 "Transport endpoint is not connected" 오류를 반환하게 됩니다. 이후 Mount를 다시 수행하면 새로운 BlobFuse2 Process가 생성되면서 정상적으로 접근이 가능하게 됩니다.

또한 전달해주신 아래 Warning 로그도 함께 확인해 보았습니다.

O_WRONLY | O_TRUNC not supported to open ... Ignoring unsupported flags.

해당 로그는 Write-back Cache가 활성화된 상태에서 지원되지 않는 Open Flag를 BlobFuse2가 무시하고 계속 처리하였다는 Warning 로그로 확인됩니다. Fatal Error가 아닌 Warning 수준의 로그이며, 발생 시점 또한 실제 장애 발생 시점보다 수 시간 이전으로 확인되어 이번 Mount Disconnect 현상과는 관련이 없는 것으로 보여집니다.

현재까지 확인된 내용으로는 BlobFuse2 Process가 종료되면서 Mount가 Orphaned FUSE Mount 상태가 된 것까지는 확인이 되었으나, BlobFuse2 Process가 종료된 정확한 원인(OOM, Process Crash, Service Restart, Manual Stop 등)은 Azure Storage Backend에서는 확인이 어려운 부분입니다.

BlobFuse2 Process가 VM 내부에서 종료되는 경우에는 Azure Storage까지 요청이 전달되지 않기 때문에 Storage Backend에는 해당 흔적이 남지 않으며, 정확한 종료 원인은 VM 운영체제 로그에서만 확인이 가능합니다.

따라서 가능하시다면 아래 로그를 확인하여 전달 부탁드립니다.

sudo journalctl -k --since "2026-07-21 01:00" --until "2026-07-22 02:00" | grep -iE 'oom|killed process|blobfuse'

sudo grep -iE 'panic|fatal|signal|oom|blobfuse2' /var/log/syslog* /var/log/kern.log*

만약 BlobFuse2를 systemd Service로 운영 중이시라면 아래 내용도 함께 전달 부탁드립니다.

sudo systemctl status <blobfuse2-service-name>

sudo journalctl -u <blobfuse2-service-name> --since "2026-07-21 01:00" --until "2026-07-22 02:00"

만약 위 로그에서 아래와 같은 내용이 확인된다면 정확한 종료 원인을 확인할 수 있을 것으로 보여집니다.

Out of memory: Killed process (blobfuse2) → OOM(메모리 부족)으로 인한 종료
panic, fatal, SIGSEGV → BlobFuse2 Process Crash
Service Stop 또는 Restart 기록 → Service 재시작 또는 운영체제 수준의 종료

현재까지 확인된 내용으로는 저희 Azure Storage 서비스 측에는 이상이 없었으며, BlobFuse2 Process 종료로 인해 Orphaned FUSE Mount가 발생한 것으로 판단됩니다.

정확한 종료 원인 확인을 위해 위 VM 로그를 전달해주시면 추가 분석을 진행하여 안내드리겠습니다.

한국마이크로소프트는 산업안전보건법에 따른 고객 응대 근로자 보호조치를 따르고 있습니다. 전화 상담 내용은 고객 지원 및 서비스 품질 향상을 위해 녹음되며, 관련 법령에 따라 일정 기간 보관됩니다. 고객께 전화를 드릴 경우 수신번호가 1577-9700(고객기술지원센터)으로 표시됩니다. 한국마이크로소프트는 개인정보처리방침을 준수합니다.
