마이크로소프트 기술지원에 문의 주셔서 감사합니다. 저는 본 케이스를 지원할 함종호 엔지니어입니다.
 
관련내용을 다음과 같이 정리하여 보내 드리니 내용을 살펴보시고 문의사항 있으면 언제든지 연락주시기 바랍니다.


본 메일의 회신은 빠른 확인을 위해 전체 회신으로 부탁드립니다.

[요청내용]

실시간 API와 관련하여 요청/응답까지 처리 시 지연건(3000ms 이상)이 간혹 발생하여

엔드투엔드 트랜잭션 세부 정보에서 보면 첨부된 이미지 붉은 박스처럼 각 단계별 사이에 비는 시간이 보여 문의를 드립니다.

 

해당 공백 부분운 어떨 때 발생을 하는건지 확인 부탁 드립니다.

 

엔드투엔드 트랜잭션 세부 정보 화면에서 모든 애플리케이션 로직, 지연, 사용자 지정 추적 정보가 정상적으로 표시되거나, 원인을 알 수 없는 타임라인 공백 없이 종속성 호출 간의 대기 시간이 명확하게 추적되어야 합니다.

 

[확인결과]
이미지의 붉은 박스 공백 구간은 Application Insights가 ‘무엇을 하고 있었는지’ 자동으로 식별하지 못한 시간입니다. 즉, 상위 HTTP 요청은 계속 진행 중이지만 그 사이에 기록된  Dependency ,  Trace ,  Exception , 사용자 정의 span이 없어서 타임라인상 비어 보일 수 있습니다. End-to-End Transaction Details는 모든 코드 라인을 자동으로 보여주는 화면이 아니라, 수집된 telemetry 항목을 시간순으로 그려주는 화면입니다.
 
그렇다면 어떤 이유로 문제의 비어있는 시간이 계측 되지 않았는지를 파악해야 합니다.
데이터를 토대로 유추해 볼 수 있는 한 가지 가능성은 sampling 되어 생략되었을 가능성입니다.
 

아래 쿼리를 app insights에 연결된 log analytics workspace에서 수행해보면 일부 sampling 되고 있는 것으로 확인 됩니다(95~99).

(sampling 되고 있지 않을 시 100이 표시 되어야 합니다.)

union AppRequests,AppDependencies,AppPageViews,AppBrowserTimings,AppExceptions,AppTraces
| where TimeGenerated > ago(1d)
| summarize RetainedPercentage = 100/avg(ItemCount) by bin(TimeGenerated,1h), Type

 

아래는 환경에 따라 sampling 하는 방법을 안내하고 있으니 어떤 환경에서 코드가 수행되는지 확인해 보시고 환경에 맞춰 sampling 여부를 확인해 보시기 바랍니다.

https://learn.microsoft.com/en-us/azure/azure-monitor/app/opentelemetry-configuration?tabs=java#enable-sampling

(java 예시)

applicationinsights-agent-3.7.8.jar 파일이 위치하는 폴더에 applicationinsights.json를 수정합니다.

sampling 부분에 값이 설정되어 있는지 확인합니다.

 

그 외에 아래와 같은 시나리오를 생각해 볼 수 있습니다.

애플리케이션 내부 처리시간: DB 호출 사이의 비즈니스 로직, DTO 변환, JSON 직렬화/역직렬화, 반복문, 데이터 가공 등

비동기 대기: await 이후 continuation 대기, ThreadPool 지연, lock/semaphore 대기

DB 호출 전후의 미계측 구간: 커넥션 풀 대기, 커맨드 생성, 결과 매핑/reader 처리, ORM materialization 등

자동 수집되지 않는 외부 호출: SDK가 자동 dependency로 잡지 못하는 커스텀 TCP/라이브러리 호출

샘플링/필터링: 일부 trace/dependency가 샘플링되거나 필터링되면 중간이 빈 것처럼 보일 수 있음(위에서 체크함)

런타임 지연: GC, CPU saturation, thread starvation, 동기 blocking 등이 요청 시간에 포함됨

 

주요 구간마다  TrackTrace , custom event, OpenTelemetry span을 추가해  DB 호출 전 ,  DB 결과 매핑 시작/종료 ,  응답 생성 시작/종료 처럼 쪼개면 붉은 박스 구간이 어떤 로직인지 식별할 수 있습니다.
 
추가로 3000ms 이상 지연 문제는 Application Insights에서 해당 operation_Id 기준으로 requests, dependencies, traces 를 함께 조회해 공백 구간 전후 timestamp를 비교하고, 서버 측 CPU/GC/ThreadPool/SQL connection pool 지표도 같이 확인하는 것이 좋습니다.
